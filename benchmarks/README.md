# Static HTTP benchmark suite

Run on Linux/WSL with Python 3.11+, GCC and optional NGINX/lighttpd binaries. No Python packages are required. The runner starts only its own server process groups, sequentially, using temporary files; it never stops an existing server. Select a free port with `--port` (default 18080). The benchmark CWebServer binds all IPv4 interfaces, like the application, so use a trusted test host.

```sh
python3 -m unittest discover -s benchmarks -p 'test_*.py'
python3 benchmarks/run.py --nginx /usr/sbin/nginx --lighttpd /usr/sbin/lighttpd
# Quick smoke test:
python3 benchmarks/run.py --duration 1 --warmup .2 --repeats 1 --sizes 1024 --concurrency 1 4
```

By default executables are discovered on PATH; use explicit paths for /usr/sbin binaries not on PATH. Omitted binaries are not compared. Install comparison packages through your normal Linux package manager if needed; the runner installs nothing. Supplied binaries that fail are recorded as failures, not silently omitted.

## Method

- Compile repository C sources with GCC `-O2 -Wall -Wextra` in a temporary directory. Change only `htons(8000)` to the selected benchmark port in a temporary copy of socket.c. Source files and the normal executable are untouched.
- Generate identical 1 KiB, 100 KiB and 1 MiB HTML fixtures for all servers. Validate an additional 4 KiB arbitrary binary fixture containing zero bytes before each run. That fixture tests byte transfer, not PNG decoding.
- Four workers per server. Plain HTTP/1.1, one request per TCP connection, client `Connection: close`, no compression or access logging. NGINX has `sendfile off`; lighttpd uses writev. All listeners use backlog 10. This controls userspace file serving rather than comparing tuned/default production configurations.
- For each size and concurrency (1, 4, 16, 64), warm up for one second, measure for ten seconds, and repeat three times with a fresh server. OS cache stays warm. Requests launched before the deadline can finish afterward; throughput uses elapsed time including draining requests.
- Validate status 200, Content-Length, every body byte and EOF on every request. Only valid responses count toward throughput and latency. Record failures separately. Any failure makes the runner exit nonzero while preserving results.
- Sample all members of the launched process group every 100 ms via `/proc`. CPU includes user/system ticks and reaped-child ticks. RSS sums server processes including supervisor and double-counts shared pages: this is RSS, not PSS or unique memory. Sampling can miss brief peaks. Short CPU samples suffer tick quantization; churn complicates accounting, so keep individual runs below the server's 120-second worker lifetime.

## Outputs

`results.json` records environment, compiler, commit, tracked source diff, versions, parameters and all repetitions. `RESULTS.md` contains comparison tables; server logs capture startup/runtime errors. Configurations are generated by `configurations()` in run.py.

The checked-in experiment uses NGINX 1.28.3 and lighttpd 1.4.82 on WSL2, with 1 KiB/100 KiB fixtures, concurrency 1/4/16, 0.5-second warmup and three 3-second repetitions (54 measured runs). It is a short local comparison. Reproduce its matrix with:

```sh
python3 benchmarks/run.py --port 18081 --nginx /path/to/nginx --lighttpd /path/to/lighttpd --duration 3 --warmup .5 --repeats 3 --sizes 1024 102400 --concurrency 1 4 16
```

The defaults intentionally run a broader, longer matrix. Regenerate the median summary without rerunning servers using `python3 benchmarks/run.py --summarize`.

| Metric | Meaning |
|---|---|
| Good requests/s | Valid successes / actual elapsed seconds |
| p50/p95/p99 ms | Nearest-rank successful latency from connection establishment through body and EOF |
| Error % | Failed attempts / attempts; details in JSON |
| CPU % (1 core) | Server CPU seconds / elapsed seconds x 100; may exceed 100% |
| Requests/CPU-s | Valid successes / server CPU seconds; larger is more efficient |
| Peak/end RSS MiB | Sampled total resident memory across server processes |
| Client CPU seconds | Load generator CPU consumption, useful for detecting saturation |

The asyncio Python client runs on the same host and can become the bottleneck. Similar throughput with a busy client does not establish equal server capacity. This is a closed-loop test, so coordinated omission applies. For capacity studies use a separate load machine, an independent load generator, longer runs, more repetitions, and record CPU affinity, hardware and background load. Compare repetition medians and spread; do not average percentiles into a pooled percentile.

No fixed performance thresholds are asserted because hardware varies. Unit tests verify fragmented binary responses are accepted and truncated, wrong and extra-byte responses rejected. They are not security or HTTP conformance tests.

## Configuration references

NGINX: [HTTP core directives](https://nginx.org/en/docs/http/ngx_http_core_module.html), [worker configuration](https://nginx.org/en/docs/ngx_core_module.html#worker_processes). lighttpd: [configuration reference](https://redmine.lighttpd.net/projects/lighttpd/wiki/Docs_ConfigurationOptions), [worker documentation](https://redmine.lighttpd.net/projects/lighttpd/wiki/Server_max-workerDetails). Matching four workers controls one variable; it does not claim this worker count is optimal.
